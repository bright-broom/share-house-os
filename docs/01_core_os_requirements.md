## 1. プロダクトの目的と提供価値

### 1.1 位置づけ

Core OSは、Share House OSエコシステム全体を支える**不可視のインフラ層**である。住民向けアプリ（Resident App）、オーナー向けSaaS（Owner Console）、集客ポータル（Acquisition Portal）の3つのフロントエンドプロダクトは、すべてこのCore OSが管理する統合データベース・決済基盤・信用スコアエンジンに接続し、データの一貫性とビジネスロジックの整合性を享受する。

エンドユーザーがCore OSを直接操作することはない。Core OSは「裏側の巨大な頭脳」として、他の3プロダクトに対してAPI・Realtime・RPC・Webhookを通じてサービスを提供する。

### 1.2 解決するペイン

| ステークホルダー | ペイン | Core OSによる解決 |
|---|---|---|
| **オーナー** | 家賃の手動回収、滞納の追いかけ、ポイント還元の手計算 | Stripe基盤による家賃自動引き落とし・ポイント割引のCoupon自動適用・滞納自動検知 |
| **オーナー** | 空室時に「良い住民」を見つけるのに毎回ゼロから募集 | アルムナイ（退去者）DBの一元管理 + 信用スコアによる優良候補者の即座のリストアップ |
| **住民** | 引越しのたびに信用情報がリセットされ、初期費用・審査の負担が繰り返される | 信用スコアのポータビリティ（持ち運び）機能。高スコア保持者はネットワーク内の別物件に低コスト移動可能 |
| **プラットフォーム運営** | 3つのフロントエンドでデータが分散し、整合性が取れなくなるリスク | Single Source of Truth としてのPostgreSQL + RLS。全プロダクトが同一DBを参照 |

### 1.3 Core OSが提供する3つのコアサービス

**① 統合決済基盤（Stripe Payment Infrastructure）**
家賃のサブスクリプション決済、初期費用のワンタイム決済、敷金の保持と返金、House Economyポイント還元（Coupon自動適用）、引越し手数料の精算——あらゆる金銭フローをStripe Connect上で一元処理する。

**② 信用スコアエンジン（Resident Trust Score Engine）**
住民の「信頼度」をデータ駆動で可視化する独自スコアリング。家賃滞納歴（ネガティブ）、House Questsの消化率（ポジティブ）、Thanks Tokensの受領数（ポジティブ）、Silent Reportでの被通報回数（ネガティブ）、入居期間（ポジティブ）などの多次元データを統合し、0〜1000のスコアを自動算出する。このスコアは他物件への移動時・アルムナイスカウト時の判断材料としてOwner Consoleに提供され、Acquisition Portalでは「ワンクリック引越し」の適格判定に使用される。

**③ アルムナイ（休眠顧客）データベース**
退去した住民のプロフィール・信用スコア・入居履歴を、本人の同意のもとでアルムナイDBとして保持する。オーナーは急な空室時に、高スコアのアルムナイに対して「スカウトオファー」（特別条件での再入居提案）を送信できる。アルムナイ側は、スコアを「ポータブル資産」として持ち運び、ネットワーク内の別物件に低コストで移動する権利を得る。

## 2. マネタイズ手法・財務インパクト

### 2.1 Core OS自体の直接収益

Core OSは直接的な課金プロダクトではないが、他の3プロダクトの収益を以下の形で下支え・増幅する。

| マネタイズ経路 | 説明 | 年間インパクト（Y5想定） |
|---|---|---|
| **Stripe決済手数料のマージン** | 全家賃決済がプラットフォーム経由で処理されることで、決済額の一部（0.5〜1.0%）をプラットフォーム手数料として徴収可能 | 約1,400〜2,800万円（※総決済額の推計に基づく） |
| **アルムナイスカウト手数料** | スカウト経由で再入居が成約した場合、1件あたり15,000〜25,000円の成功報酬 | 約300〜600万円（年間200〜400件の再入居想定） |
| **信用スコアの外部提供（将来構想）** | 他の不動産プラットフォーム・保証会社に対し、匿名化されたスコアデータをAPI提供する可能性（Phase 4以降の検討事項） | 未定（データ資産としての潜在価値） |

### 2.2 財務インパクト：チャーン率とLTVへの構造的貢献

Core OSの最大の財務貢献は、**信用スコアのポータビリティがプラットフォーム全体の「囲い込み力」を高める**ことにある。

住民にとって、長期間の良好な居住実績で積み上げた信用スコアは「ネットワーク内でのみ有効な資産」であり、ネットワーク外の物件に引っ越すとゼロにリセットされる。この「スコアを捨てたくない」心理が、住民のネットワーク内定着率を構造的に高める。

| 指標 | Core OS無し | Core OS有り | 改善幅 |
|---|---|---|---|
| 住民の年間退去率 | 45% | 30% | △15pt |
| うちネットワーク内移動率 | 0% | 10% | +10pt（退去ではなく移動。空室が即埋まる） |
| 実質ネットワーク離脱率 | 45% | 20% | △25pt |
| オーナーの月次SaaSチャーン | 3.0% | 2.0% | △1.0pt（空室リスク低減がSaaS継続動機を強化） |

### 2.3 コスト構造

| コスト項目 | 月額（Y3想定） | 備考 |
|---|---|---|
| Supabase Pro/Team | 20,000〜40,000円 | PostgreSQL、Auth、Realtime、Storage |
| Stripe手数料（決済処理） | 決済額の3.6% | オーナーからの回収分で相殺 |
| Edge Functions / Cron | Supabase料金に含む | ポイント集計、スコア更新、アラート配信 |
| AI Scoringサービス（Phase 3〜） | 30,000〜50,000円 | Cloud Run / Fly.io |

**スコア算出モデル：ベーススコア＋加減点＋ペナルティ乗数方式**

単純なパーセンテージ重み付けではなく、エンジニアが実装しやすい**3層構造のスコアリングモデル**を採用する。

**Step 1: ベーススコアの設定**
全住民の初期スコアを **600点** とする（入居開始時点）。

**Step 2: 加点要素（ポジティブ行動で最大+400点）**

| 加点要素 | 最大加点 | 算出ロジック | データソース |
|---|---|---|---|
| 入居期間 | +80点 | `min(入居月数 × 4, 80)` — 20ヶ月で上限到達 | house_memberships |
| House Quests消化率（過去90日） | +100点 | `消化率(0.0〜1.0) × 100` | quest_claims |
| Thanks Tokens受領数（過去90日） | +80点 | `min(受領数 × 8, 80)` — 月平均3〜4件で上限到達 | thanks_tokens |
| Buddy System完了回数 | +60点 | `min(完了回数 × 20, 60)` — 3回で上限到達 | buddy_assignments |
| Rule Governance投票参加率（過去90日） | +40点 | `参加率(0.0〜1.0) × 40` | rule_votes |
| **加点合計上限** | **+400点** | — | — |

**Step 3: ペナルティ乗数（重大違反はスコアを乗数で圧縮）**

重大なネガティブ行動は加減点ではなく**乗数（Multiplier）**として適用する。これにより、家賃滞納1回のような重大事象がスコアに与えるインパクトを十分に大きくしつつ、複数回の違反で指数的にスコアが下がる仕組みを実現する。

| ペナルティ要素 | 乗数 | 適用ロジック | データソース |
|---|---|---|---|
| 家賃滞納（過去12ヶ月） | **× 0.7^n**（nは滞納回数） | 1回で30%減、2回で51%減、3回で66%減 | Stripe Webhook (invoice.payment_failed) |
| Silent Report被通報（過去90日、確認済みのもの） | **× 0.9^n**（nは被通報回数） | 1回で10%減、3回で27%減 | silent_reports（reported_user_id別に集計。通報者の匿名性は維持） |

**最終スコア算出式：**
```
raw_score = base(600) + 加点合計(0〜400)
final_score = round(raw_score × 滞納乗数 × 被通報乗数)
final_score = clamp(final_score, 0, 1000)
```

**算出例：**
- 入居12ヶ月、Quest消化率80%、Thanks月3件、Buddy1回、投票60%、滞納0回、被通報0回
  → `600 + 48 + 80 + 72 + 20 + 24 = 844` × 1.0 × 1.0 = **844点**
- 同条件で家賃滞納1回
  → `844 × 0.7 = 591` → **591点**（滞納の破壊力が明確）
- 入居3ヶ月、Quest消化率30%、他ゼロ、滞納0回
  → `600 + 12 + 30 + 0 + 0 + 0 = 642` → **642点**（新入居者でも中程度）

**重要な設計原則：**
- スコア算出に性別・国籍・年齢・MBTI等の属性情報は一切使用しない。行動データのみに基づくスコアリングとし、差別的運用を構造的に排除する。
- Phase 3以降のAI高度化（LightGBM等）においても、保護属性の入力は禁止し、公平性監査（Demographic Parity）を四半期ごとに実施する。
- 乗数・加点の上限値はオーナーによるカスタマイズ不可（プラットフォーム統一基準）。変更はADRで審議の上、全物件に一括適用する。

### 4.3 信用スコア算出のアーキテクチャ

```
[日次 Cron Trigger (00:00 JST)]
      │
      ▼
[Edge Function: calculate-trust-scores]
      │
      ├── 【Step 1】 ベーススコア = 600（全住民共通）
      │
      ├── 【Step 2: 加点要素の集計】
      │   ├── house_membershipsから入居月数 → min(月数×4, 80)
      │   ├── quest_claimsから過去90日のQuest消化率 → 消化率×100
      │   ├── thanks_tokensから過去90日の受領数 → min(受領数×8, 80)
      │   ├── buddy_assignmentsから完了回数 → min(回数×20, 60)
      │   ├── rule_votesから過去90日の投票参加率 → 参加率×40
      │   └── 加点合計（上限400点）
      │
      ├── 【Step 3: ペナルティ乗数の算出】
      │   ├── Stripe APIから過去12ヶ月の滞納回数(n) → 乗数 = 0.7^n
      │   ├── silent_reportsから過去90日のreported_user_id別
      │   │   被通報回数(m, statusがacknowledged以上のもの) → 乗数 = 0.9^m
      │   └── ※通報者の匿名性は維持。被通報者IDは通報時に記録
      │
      ├── 【最終算出】
      │   final_score = clamp(round((600 + 加点合計) × 0.7^n × 0.9^m), 0, 1000)
      │
      ▼
[trust_scoresテーブルをUPSERT（components JSONBに各要素の内訳を保存）]
[trust_score_historyテーブルにINSERT（日次スナップショット）]
      │
      ▼
[スコア変動が一定閾値（±50点）以上の場合、住民にプッシュ通知]
```

### 4.5 セキュリティ・法的考慮事項

- **信用スコアの公平性：** 性別・国籍・年齢等の保護属性をスコアリングに使用しない。公平性監査（Demographic Parity）を四半期ごとに実施。
- **アルムナイデータの保持：** 個人情報保護法に基づき、本人のオプトイン同意を退去時に取得。オプトアウト（データ削除）は随時可能。
- **スコアの目的外利用の禁止：** 信用スコアはShare House OSネットワーク内の入居判断にのみ使用し、外部への提供は本人同意なしには行わない（将来のAPI提供時にも匿名化・同意取得を徹底）。
- **敷金のStripe上プールに関する法務注記：** 敷金（預かり金）をプラットフォーマーがStripeのCustomer Balance上で長期保持するスキームは、日本の資金決済法における「為替取引」規制およびStripe JP利用規約（預かり金の長期滞留に関する条項）に抵触するグレーゾーンが存在する。実装前に以下を必ず確認する：(1) Stripe JPサポートへの個別確認（Customer Balanceでの敷金保持が利用規約上許容されるか）、(2) 弁護士による資金決済法上のリスク評価、(3) 代替スキームとして「敷金のみオーナー銀行口座に直接振込、その他はStripe経由」のハイブリッド型を検討。敷金の扱いは契約成立の根幹に関わるため、法務確認完了までMVPでは敷金決済機能を保留し、手動振込フローで代替する。
- **ポイント還元と資金決済法：** ポイントは「翌月家賃からの割引」としてのみ機能し、現金化・外部利用不可の設計とすることで、前払式支払手段への該当を回避。法務チームと継続的に確認。
